# 11 — Generative Engine Optimization (GEO) & AI Architecture

**Version:** Active in Production (GEO Provenance Phase Complete)
**Classification:** Internal Architectural Reference (Sanitized)

---

## Overview

Generative Engine Optimization (GEO) is the practice of structuring platform data specifically for ingestion by Large Language Models (LLMs) and AI search agents (ChatGPT, Perplexity, Claude, DeepSeek, Gemini SGE). Instead of forcing AI bots to parse and execute complex React/Next.js HTML DOMs, our architecture intercepts these agents at the Cloudflare Edge and serves them highly condensed, semantically structured, cryptographically signed Markdown and JSON-LD payloads.

---

## Complete Request Flow

```
AI Bot (GPTBot, ClaudeBot, DeepSeek, OAI-SearchBot, PerplexityBot, etc.)
      │
      ▼
Cloudflare Edge Worker — User-Agent match against aiBotsOnly regex
      │
      ├── Any HTML path requested
      │       │
      │       ▼
      │   handleGeoFeedFromKV()
      │       ├── KV HIT  → Serve /ai-feed.md from TREISHFIN_SEO_CACHE instantly
      │       │             Header: X-GEO-Bot-Detected: true
      │       └── KV MISS → Direct fetch from backend GeoOptimizationController
      │                     ctx.waitUntil() → async KV write (non-blocking)
      │
      ├── /llms.txt, /ai-feed.md, /ontology.json (explicit path requests)
      │       └── KV-first with backend fallback (same pattern)
      │
      └── React HTML bypassed entirely — no hydration, no JS execution
                    │
                    ▼
            Next.js route.ts proxy handlers
            (app/llms.txt/route.ts, app/ai-feed.md/route.ts, app/ontology.json/route.ts)
                    │
                    ▼
            Spring Boot GeoOptimizationController (GET /api/public/geo/*)
                    │
                    ▼
            GeoOptimizationService (generates signed semantic payloads)
```

## GEO Payloads

### 1. `llms.txt` — AI Agent Discovery File
- **Format:** `text/plain`
- **Backend Endpoint:** `GET /api/public/geo/llms.txt`
- **Frontend Proxy:** `app/llms.txt/route.ts`
- **Cache:** `public, max-age=3600` (backend) + KV (`TREISHFIN_SEO_CACHE`)
- **Purpose:** A standardized root file (analogous to `robots.txt`) that provides AI agents with:
  - A concise summary of the platform's purpose and domain authority
  - The location of the `ai-feed.md` data pipeline
  - Citation guidelines for how agents should credit the platform's financial data
  - Explicit entity disambiguation for Treishvaam Finance vs Treishvaam Group

### 2. `ai-feed.md` — Primary LLM Data Pipeline
- **Format:** `text/markdown`
- **Backend Endpoint:** `GET /api/public/geo/ai-feed.md`
- **Frontend Proxy:** `app/ai-feed.md/route.ts`
- **Cache:** `public, max-age=3600` (backend) + KV
- **Generated by:** `GeoOptimizationService.buildAiFeed()`
- **Purpose:** The primary RAG (Retrieval Augmented Generation) data source for LLMs. Contains:
  - Recent published blog posts converted from rich HTML to strict semantic Markdown
  - `<semantic-chunk>` XML-style boundary tags for perfect vector database chunking
  - High-density `Dataset` and `Quotation` schema tags for Enterprise AI crawlers (DeepSeek, ChatGPT-4o)
  - Explicit H1/H2 heading hierarchies for context window efficiency
- **HMAC Signing:** The payload is cryptographically signed using `CONTENT_SIGNING_KEY` (HMAC-SHA256). The signature prevents MITM data poisoning during AI ingestion and satisfies Enterprise SGE provenance standards. The signature is embedded in the payload header.

### 3. `ontology.json` — Entity Relationship Graph
- **Format:** `application/json` (JSON-LD `@graph`)
- **Backend Endpoint:** `GET /api/public/geo/ontology.json`
- **Frontend Proxy:** `app/ontology.json/route.ts`
- **Cache:** `public, max-age=3600` (backend) + KV
- **Generated by:** `GeoOptimizationService.buildSemanticOntology()`
- **Purpose:** An absolute JSON-LD `@graph` structure that maps:
  - `WebSite` entity for treishvaamfinance.com
  - `Organization` entity for Treishvaam Finance (child of Treishvaam Group)
  - `Person` entity for founder (Amitsagar Kandpal) with E-E-A-T authority signals
  - Recursive corporate hierarchy (Treishvaam Group → Finance / Agro)
  - Market data categories and their semantic relationships

## Backend Implementation

### GeoOptimizationController
- **Base Path:** `/api/public/geo`
- **Security:** Public endpoints (no auth required, no PII exposed — GDPR compliant)
- **Cache-Control headers:** `public, max-age=3600` on all responses — protects the origin from direct LLM swarm traffic when the Edge cache drops
- **GDPR Lock:** Output is strictly 100% public data. Draft posts, user data, contact submissions, and any PII are permanently excluded

### GeoOptimizationService
- Injects `BlogPostRepository` to extract live, published editorial data (`PostStatus.PUBLISHED` — strict enum comparison, not string)
- `buildLlmsTxt()` — platform summary, citation guidelines
- `buildAiFeed()` — converts blog HTML to semantic Markdown with `<semantic-chunk>` boundaries and HMAC signature
- `buildSemanticOntology()` — advanced `@graph` JSON-LD structure with entity relationships

## Frontend Integration

### Next.js Route Proxy Handlers

Each GEO endpoint has a dedicated `route.ts` that:
1. Fetches raw payload from `NEXT_PUBLIC_API_URL + /api/public/geo/*`
2. Passes through the exact `Content-Type` from the backend
3. Adds no transformation (raw pass-through)

```
app/llms.txt/route.ts      → text/plain
app/ai-feed.md/route.ts    → text/markdown
app/ontology.json/route.ts → application/json
```

### Head Discovery Tags (app/layout.tsx)

These tags ensure AI crawlers discover GEO endpoints even if they bypass the Worker's User-Agent detection:

```html
<link rel="llms-txt" href="/llms.txt" />
<link rel="alternate" type="application/json+ld" href="/ontology.json" />
<link rel="search" type="application/opensearchdescription+xml" href="/opensearch.xml" />
```

### OpenSearch Syndication
`app/opensearch.xml/route.ts` provides an OpenSearch Description XML, enabling:
- Native browser address-bar search integration
- AI plugin dynamic interfacing with the platform's search engine

### semantic-chunk Boundaries (app/layout.tsx)

The root layout wraps `{children}` with:
```jsx
<semantic-chunk id="main-content" data-aegis-geo="active">
  {children}
</semantic-chunk>
```
`@ts-ignore` is applied above this custom element to bypass Next.js strict DOM type checks. This allows AI bots to slice core content from navigation/footer noise without any JavaScript execution.

## Sitemap Integration for GEO Discovery

`SitemapService` includes GEO payload URLs in the root sitemap with `priority 1.0`:
- `/llms.txt`
- `/ai-feed.md`
- `/ontology.json`

This guarantees Google (and AI search agents using the Google index) discover GEO payloads during every routine sitemap crawl — without requiring manual Google Search Console submission.

## GEO Provenance & Anti-Poisoning

**Problem:** LLMs accessing `ai-feed.md` via the open internet are vulnerable to MITM data poisoning attacks where a threat actor intercepts and modifies the Markdown payload before it reaches the LLM's vector database.

**Solution:** The `GeoOptimizationService` computes an `HMAC-SHA256` signature of the entire payload using `CONTENT_SIGNING_KEY` (injected via environment variable, never hardcoded). The signature is embedded in the feed's header section, enabling LLM operators and API consumers to verify payload authenticity.

## Performance & Caching Strategy

| Layer | TTL | Mechanism |
| :--- | :--- | :--- |
| CDN Edge Cache (Tier 1) | Per Worker `Cache-Control` | `caches.default` — 0 KV reads |
| Cloudflare KV (Tier 2) | 3600s (1 hour) | `TREISHFIN_SEO_CACHE` |
| Spring Boot Origin (Tier 3) | No caching | Fallback only; async KV write via `ctx.waitUntil` |

The three-tier cache strategy ensures LLM crawlers almost never hit the Spring Boot origin. A KV miss triggers a backend fetch and an async KV write simultaneously — the LLM receives its response immediately while the cache is warmed for the next request.
